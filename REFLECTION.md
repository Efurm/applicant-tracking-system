## Project #1: Applicant Tracking System.

Question 1 - Trace your Django forms. Find one class in your project that inherits from forms.Form and one that inherits from forms.ModelForm. For each form, identify what it does and trace how it is used through the application. Explain the important difference between the two forms in your own words. The AuthenticationForm inherits from forms.Form and it checks a username and password to log the user in. django.contrib.auth.urls maps accounts/login/ to the LoginView which uses AuthenticationForm which then draws the form using the login template and then on POST the clean() calls authenticate() to verify the account to reject bad or inactive accounts and calls login() if it is a valid account. CandidateForm inherits from forms.ModelForm and it creates and edits the Candidate records. tracker/views.py pulls CandidateForm(_form_data(request)) which then runs through processes and checks to create a valid candidate form and then views.py pulls the CandidateForm(_form_data(request),instance=candidate) which fills the form with the candidate's current values. The most important difference between the two is that forms.Form is defined by me and takes input while forms.ModelForm is built from a model and only uses fields and data from that model.

Question 2 - Trace a many-to-many relationship. Identify a many-to-many or association-table relationship in your ATS. Explain which models are connected and why a single foreign key would not represent the relationship correctly. Identify the association table or model and explain whether Django created it automatically or your project defines it explicitly. If it is an explicit association model, explain what data belongs to the relationship itself. Application is a many-to-many relationship in my ATS. The Candidate and JobOpening models are connected and a single foreign key would not work because a candidate can apply to many jobs and a job can get many candidates, and using a single foreign key would force them into a one on one relationship such as a candidate only being able to apply to one job and a job only being able to get one candidate which would not fit a realistic hiring pipeline. Application is defined explicitly with stage,source,source_details,applied_on,created_at,updated_at being data the belongs to the relationship itself that shows where the application is in the pipeline, how the candidate found the job, and when the application happened as well as when it was last changed.

Question 3 - Explain one prototype decision. Choose either your application-state prototype or your UI prototype. What specific design question was the prototype built to answer? Describe the alternatives you explored, the decision you made after using the prototype, and where that decision appears in your PRD or completed application. The specfic design question for the prototype of the UI was "what should the main screen for moving applications through the hiring pipeline look like?" The alternatives explored was one column per stage for a single job with application cards in the columns for the first alternative, and picking a job from a sidebar which you can then see its application in a table with a stage column as the second alternative. I chose to have a searchable,filterable list of applications from every job on the left, and a detail panel for the selected application on the right. It appears in the PRD on lines 200-203 and line 265.

Question 4 - Defend one code-design decision. Choose one architecture or code-structure decision from your project where the agent recommended one or more options. Explain the options, the decision you approved, and why that choice fits your project. Identify where that decision appears in the completed code. Question 13 was about how stage history is recorded. The options were: Store only the current stage with no history, A StageChange log that writes a row with the old stage, the new stage, the user, the time, and an optional note, and the last option was to have a full audit log of every field change for a hiring team to view a log of every single edit to the model. I approved the StageChange log because it protects the history, it shows the log allowing an easy understanding of the processes a application has gone through, all while fulfilling the PRD requirement. It appears in the model.py itself and services.py is where is it written, where then application_move uses it in views.py, and then after it is displayed in tracker/templates/tracker/applications/_panel.html .
